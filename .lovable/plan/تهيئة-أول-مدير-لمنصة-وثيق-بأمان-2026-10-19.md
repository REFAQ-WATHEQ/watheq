# تهيئة أول مدير لمنصة وثيق بأمان

## حدود هذه الموافقة
هذه خطة للتنفيذ اللاحق، وليست تعيينًا لأي حساب. الموافقة عليها تسمح بإضافة الحماية والاختبارات فقط؛ تنفيذ التهيئة على WATHEQ يحتاج موافقة منفصلة تحدد UUID الحساب الحقيقي بعد التحقق منه. لا نشر، ولا مشروع إنتاج جديد، ولا تغيير للدخول أو الهوية أو إتاحة المحتوى.

## نتيجة الفحص المباشر
- قاعدة البيانات الحالية تحتوي حسابًا واحدًا، وصفر مدير وصفر مدير نشط. لم تُغيّر أي أدوار.
- الدور المستخدم فعليًا هو `admin` ويقابل `platform_admin`؛ و`supervisor` يقابل المشرف. لا حاجة لتغيير أسماء الأدوار أو إعادة تأسيسها.
- الأدوار منفصلة في `public.user_roles`. القيد `UNIQUE(user_id, role)` لا يمنع تعدد المديرين.
- تغيير الأدوار المعتاد يمر من `changeRole` إلى `public.set_account_role` ثم الإجراء الخاص، بجلسة الطالب نفسه. قاعدة البيانات تعيد التحقق من مدير مؤكد البريد وغير محظور وغير محذوف، وتمنع التغيير الذاتي وتتحقق من الحساب المستهدف، وتسلسل التغييرات بالقفل `(184910,1)`.
- سياسات جدول الأدوار تسمح بالقراءة فقط للحسابات العادية؛ لا توجد صلاحية INSERT/UPDATE/DELETE لـ`anon` أو `authenticated`. استدعاء إجراء تغيير الدور غير مسموح للزائر أو لحساب الخدمة، ومسموح للمسجلين مع تحقق داخلي من المدير.
- مشغلات صفوف الأدوار تتحقق من أهلية المدير الجديد وتحمي آخر مدير وتكتب تدقيقًا. حذف الحساب الذي يحذف دوره بالتتابع يمر أيضًا بهذه المشغلات؛ ليس تجاوزًا عامًا للحماية.
- التهيئة الموثقة حاليًا تعتمد على بريد في الملف الشخصي ثم فحص الحساب، وتكتب الدور مباشرة من SQL Editor. لا تحتوي قفلًا قبل فحص غياب المدير ولا علامة دائمة لاستهلاك التهيئة؛ لذلك سنستبدل التعليمات ولا ننفذها.
- الاختبارات الـ36 السابقة ليست إثباتًا لتشغيل التهيئة أو حماية PostgreSQL: اختبارات الأدوار الحالية قواعد محلية، وبعض اختبارات الحماية تفحص نصوص الملفات. الاختبار المصادق عليه لتعدد المديرين لم يكتمل.

## التحذيرات الأمنية الثلاثة الحالية — دون تعديل
أُعيد تشغيل فاحص Supabase، وهذه أسماؤه الحالية، وليست ثلاثة تحذيرات مستقلة بينها تحذير رابع باسم RLS Auto Enable:

1. **Public Can Execute SECURITY DEFINER Function** — `0028_anon_security_definer_function_executable`.
2. **Signed-In Users Can Execute SECURITY DEFINER Function** — `0029_authenticated_security_definer_function_executable`.
   كلاهما مرتبط، وفق تعريفات الدوال وصلاحياتها الحالية، بـ`public.rls_auto_enable()` ذات صلاحية التنفيذ العامة الافتراضية. تعمل بصلاحية مالكها لتفعيل RLS عند إنشاء الجداول. نوعها `event_trigger`؛ ليست إجراء تعيين مدير ولا دالة RPC عادية يستطيع الزائر تشغيلها مباشرة. الصلاحيات الواسعة تستحق مراجعة منفصلة، لكنها لا تثبت وحدها إمكانية ترقية مستخدم. لم أغيّرها.
3. **Leaked Password Protection Disabled** — كلمات المرور الجديدة أو المعدلة لا تُفحص ضد قوائم التسريبات المعروفة، ما يزيد خطر اختراق الحسابات بإعادة استخدام كلمات المرور. لا تمنح صلاحية مدير مباشرة. لم أغيّر إعدادها.

نتائج الفحص الأمني المحفوظة بتاريخ 18 أكتوبر تتضمن أيضًا ملاحظات أقدم على قراءة الفئات وشعارات الهوية، وموسومة بأنها غير محدثة؛ ليست بديلًا عن التحذيرات الثلاثة الحالية ولا شهادة بأن المنصة خالية من المخاطر.

## ما معنى «الحظر المباشر خارج الحماية»؟
الحماية الحالية تراقب تغييرات جدول الأدوار، لا تغييرات حالة الحساب في `auth.users`. الحظر من لوحة Supabase أو Auth Admin API يمكن أن يجعل آخر مدير غير نشط مع بقاء صف دوره؛ عندها يرفض إجراء إدارة الأدوار استعماله. وكذلك حذف الحساب حذفًا لينًا أو تغيير تأكيد بريده قد يغيّر أهليته دون تعديل الدور. أما الحذف الفعلي المتسلسل لدوره فمشغلات الحماية الحالية تغطيه عند عملها طبيعيًا.

مسارات أخرى ذات صلاحية أعلى من واجهة الإدارة:
- `service_role` يملك حاليًا INSERT/UPDATE/DELETE على جدول الأدوار ويتجاوز RLS: الكتابة المباشرة لا تمر بفحص هوية المدير في إجراء تغيير الدور، وإن كانت مشغلات الصفوف ما زالت تتحقق من الأهلية وآخر مدير. لا يوجد دليل على تعريض هذا المفتاح للمتصفح.
- **فجوة مؤكدة في GRANT:** الأدوار `anon` و`authenticated` و`service_role` تملك TRUNCATE وTRIGGER على جدولي الأدوار والتدقيق. TRUNCATE لا يخضع لـRLS ولا لمشغلات INSERT/UPDATE/DELETE؛ عبر اتصال SQL أو إجراء مكشوف يمنح هذه العملية يمكن تفريغ الجدول وتجاوز الحماية أو محو التدقيق. لا يوفّر REST المعتاد عملية TRUNCATE، ولم أجد إجراءً مكشوفًا لها؛ وجود GRANT لا يعني أن مستخدم المتصفح يستطيع تنفيذ SQL اعتباطيًا. يجب سحبها مع ذلك.
- التدقيق الحالي لا يسجل نقل صف `admin` إلى UUID آخر إذا بقي نص الدور `admin` كما هو. سنغلق نقل ملكية صف الدور ونختبره.
- مالك قاعدة البيانات أو مشغل يملك تغيير التعريفات يستطيع تعطيل المشغلات أو إعادة منح الصلاحيات. لا يمكن للتطبيق منع مالك البنية من تغييرها. وAuth Admin API بصلاحية الخدمة يظل خارج حماية جدول الأدوار؛ يجب عدم حظر آخر مدير منه قبل وجود بديل، وهذه حدود واضحة وليست ضمانًا مطلقًا.

## المسار المقترح: تهيئة واحدة من مالك قاعدة البيانات فقط
لا زر في الحساب، ولا رابط تهيئة عام، ولا كلمة مرور تهيئة، ولا إجراء خادمي يستخدم مفتاح الخدمة للتعيين.

1. إضافة إجراء داخل `private` ينفذه مالك قاعدة البيانات الموثوق من SQL Editor فقط، بنمط SECURITY INVOKER وفحص سلطة التنفيذ الفعلية. سحب EXECUTE من PUBLIC والزائر والمسجل وحساب الخدمة، والتحقق من الصلاحيات الفعلية بعد الهجرة.
2. يستقبل UUID ثابتًا وافقت عليه صراحة، لا بريدًا ولا ادعاءً من المتصفح. يتحقق من سجل `auth.users` الأصلي ومن وجود الملف الشخصي، وتأكيد البريد، وعدم الحذف أو الحظر. تأكيد البريد يثبت أهلية الحساب التقنية؛ موافقتك على UUID هي اعتماد هوية المدير إداريًا.
3. يأخذ القفل نفسه قبل قراءة حالة التهيئة وعدد المديرين، ويقفل صف الحساب أثناء التحقق. يرفض إذا وجد أي مدير، حتى غير نشط، أو إذا استُهلكت التهيئة سابقًا.
4. إنشاء سجل حالة مفرد خاص غير مكشوف للتطبيق، يمنع إعادة التهيئة بعد النجاح ولو اختفت الأدوار لاحقًا. إذا وُجد مدير عند تثبيت الهجرة، يُنشأ السجل مغلقًا بدل فتح مسار إضافي.
5. في معاملة واحدة: تعيين الدور للحساب المحدد مع حفظ بقية بياناته، تسجيل عملية التهيئة وهوية منفذها الإدارية وUUID المستهدف والوقت، ثم إغلاق الحالة. أي فشل يتراجع عن الجميع. علامة الإغلاق ليست إعدادًا يفتحه المستخدم أو حساب الخدمة؛ يستطيع مالك قاعدة البيانات تغيير البنية خارج التطبيق، وتلك حدود الثقة.
6. بعد النجاح، الإجراء يرفض كل إعادة استعمال. إدارة المديرين التالية تبقى عبر المسار الحالي للمديرين، ولا يتحول إجراء التهيئة إلى مسار استعادة أو تعيين ثانٍ.

## التعديلات التقنية المحدودة
- **هجرة واحدة عبر أداة Supabase:** إجراء التهيئة وحالتها داخل `private` مع صلاحيات صريحة، وسحب TRUNCATE/TRIGGER والصلاحيات الزائدة غير اللازمة من جدولي الأدوار والتدقيق؛ سحب الكتابة المباشرة لـ`service_role` على الأدوار، والإبقاء على التعديل عبر الإجراء المصادق عليه. مشغل إنشاء الحساب يعمل بصلاحية مالكه، ويُختبر حتى لا يتعطل التسجيل.
- تقوية مشغل الأدوار لمنع تغيير `user_id` لصف قائم؛ معالجة سجل التدقيق لتمييز التهيئة والمنفذ الموثوق دون الثقة في قيمة يرسلها العميل، مع الحفاظ على السجل الحالي وسياسة قراءة المديرين. لا دور على الملفات الشخصية ولا تغيير لإتاحة المحتوى.
- إضافة اختبارات مركزة بجوار `src/test/role-management.test.ts`، ومواد تشغيل الاختبارات المعزولة فقط عند الحاجة.
- تحديث `FOUNDATION-DELIVERY.md` لاستبدال تعليمات البريد القديمة بتعليمات UUID والتحقق والموافقة المنفصلة وحدود الحظر الإداري، وتحديث `AGENTS.md` و`roadmap.md`.
- لا تعديل لواجهة المديرين أو `functions.ts` إلا إذا أثبت اختبار ضرورة توافق محددة. لا تعديل للتحذيرات الثلاثة في هذا العمل دون موافقة إضافية.

## خطة اختبارات تثبت حماية فعلية
بعد الموافقة، تُشغّل الاختبارات التي تغير الأدوار على قاعدة Supabase/PostgreSQL اختبارية معزولة ببيانات مصطنعة وأدوار وصلاحيات ومشغلات مماثلة. ليست مشروع إنتاج بديلًا، ولا تُستخدم حسابات WATHEQ الحالية. إذا تعذرت بيئة الاختبار أو API مماثلة، نذكر الجزء غير المختبر ولا نستبدله باختبار نصوص أو واجهة.

- نجاح التهيئة بواسطة السلطة المعتمدة وUUID موجود مؤكد؛ رفض حساب مجهول أو غير مؤكد أو محظور أو محذوف أو بلا ملف شخصي.
- رفض التهيئة من الزائر والمستخدم والمشرف وحساب الخدمة، ورفض تغيير UUID أو الاعتماد على بريد أو بيانات ملف لتجاوز الفحص.
- محاولة تهيئة ثانية ومحاولتان متزامنتان: نجاح واحد فقط؛ رفض إعادة فتحها ولو تغيرت الأدوار لاحقًا؛ فشل العملية لا يترك دورًا أو علامة نجاح أو سجلًا جزئيًا.
- مدير مهيأ يعيّن مديرًا ثانيًا، ثم يلغي المدير الثاني وفق الضوابط؛ رفض التغيير الذاتي وإلغاء آخر مدير نشط، بما يشمل الطلبات المتزامنة والحذف الفعلي المتسلسل.
- استدعاءات فعلية إلى `set_account_role` عبر RPC وإلى دالة التطبيق بجلسات المستخدم والمشرف والزائر: رفض الترقية مع قراءة الأدوار مجددًا لإثبات عدم تغيرها. اختبار دالة التطبيق يستلزم تطبيق اختبار مرتبطًا بالبيئة المعزولة.
- محاولات SQL بالأدوار الحقيقية للكتابة المباشرة وTRUNCATE وتغيير UUID؛ وفحص effective privileges وRLS، وليس وجود نص REVOKE فقط. رفض حساب الخدمة للتهيئة وللكتابة المباشرة بعد التقييد.
- سجل التدقيق: بيانات المنفذ والمستهدف والانتقال صحيحة، لا سجل نجاح عند فشل المعاملة، لا تعديل/حذف/تفريغ من أدوار التطبيق أو الخدمة، والقراءة للمدير فقط. استمرار إنشاء الحساب العادي بدور مستخدم وصلاحيات المحتوى السابقة.

التحقق النهائي على WATHEQ بحساب مدير فعلي **يبقى خطوة منفصلة غير منفذة** حتى تعتمد UUID وتجيز التهيئة واستخدام الحسابات الاختبارية المطلوبة. لا طلب لكشف أسرار أو إرسال كلمات مرور في المحادثة.

## معيار التسليم
تقرير يفصل الاختبارات المحلية عن اختبارات قاعدة البيانات وRPC وعن تجربة WATHEQ الفعلية؛ يذكر أي عائق أو مسار امتياز إداري خارج الضمان. لا ادعاء باكتمال التعيين الفعلي قبل حصوله بموافقتك.
